4. `refs/CLT_SYK.tex` と `refs/sections/` の関係箇所

## 正式な参照元

- `refs/CLT_SYK.tex` は現在の論文の親ファイルであり、共通のプリアンブルを記録する。`refs/sections/` は本文を記録する。両者を合わせたものを定理文の正式な参照元とする。
- `ARCHITECTURE.md` は意図した証明依存関係と各結果の現在の状態を記録する。
- `../EDITING_PLAN.md` は横断的な作業単位、その前提と状態を記録する。開始時に指定 ID と対応する詳細計画を読む。
- `EDITING_PLAN.md` は既知の問題、数学的な細目、作業の完了条件と現行の検証状態を記録する。完了済み作業の詳しい経緯は [作業履歴](../WORK_HISTORY.md) の該当節を参照する。
- Lean ファイルは、Lean のカーネルが検査した正確な定理文についてのみ証明状態を記録する。

これらが一致しない場合、黙って一つを選んだり統合したりせず、不一致を報告する。

## 保護する数学的内容

明示的な承認なしに、`M_N`、`sigma_N`、`H_N`、`Z_N`、`Y_N` の定義、スケーリング `N^(q/2-1)`、極限分散、逆温度の範囲、相対ゆらぎ・標準化したゆらぎ・対数のゆらぎに対する中心極限定理（CLT）の区別、および各結果の収束の種類を変更しない。

各ゆらぎの定義、極限分散、中心化の差は `ARCHITECTURE.md` の「現行原稿の主張」と「対数 CLT の新しい経路」を参照する。

現行 CLT の実装・原稿は実数 `β` と高温条件 `|β| < βq` を用いる。以前の非負逆温度への移行案を理由にこの範囲を変更しない。共有模型の物理的 Gibbs・集中 API の `β : ℝ≥0` は維持し、CLT の実数逆温度の結果は必要な適用を明示して導く。解析の `z : ℂ` と確率論の `β : ℝ` は区別する。

CLT の規格化分配関数は一般の非空有限次元 `MajoranaSystem` に対して既に実装され、実際の次元で割る。標準表現への特殊化による原稿との対応と、一般表現への外部極限定理の適用可能性を別に照合する。W06 の有限模型の成果に、未証明の最終 CLT や `AnnealedInput` を使わない。

複素対数微分に現れる `Z z ≠ 0` は定理の仮定として明示し、零点のない領域が証明されていない段階で自動的に満たされるものとして扱わない。

## 証明と未完了事項の確認

証明を変更・説明する際は `ARCHITECTURE.md` の分解と依存関係を確認する。高次カオスの剰余項には、`refs/sections/higher-chaoses.tex` のラデマッハ変数による符号化と指数モーメントによる直接評価を用いる。対数 CLT は有効な本文の `Z_N≥1` と小確率事象による新証明を基準にする。`main-results.tex` の `\iffalse` 内の集中評価を使う旧証明は履歴であり、必須依存として扱わない。

作業前に `EDITING_PLAN.md` の未完了事項を確認する。定理文に関わる問題の調査と修正案の作成は、指定された範囲で進めてよい。ただし、その修正を単なる誤植修正として処理せず、定理文や採用する前提を変更する前に人間の研究者の承認を得る。判断事項は該当項目にまとめ、別の承認済み作業まで一律に停止させる前提にしない。

## 共同実装の着手条件

R01–R05 は原稿・外部入力の監査、F01–F08 は成果の枠であり、番号だけでは直ちに実装可能な証明仕様にならない。共同研究者から `F01 を進めて` などの短い依頼を受けた場合も、[全体計画](../EDITING_PLAN.md#共同実装の割当方法)と [担当別作業票](EDITING_PLAN.md#担当別作業票とコード整理)の該当節を読み、対応する監査、前提の統合、正確な定理文・入力、編集担当、検証対象を確認してから実装する。足りなければ指定課題内の調査と障害の報告まで進め、未承認の仮定・定理文を仮置きしてコードを書かない。単なる `CLT の続きを実装` という依頼では、全体計画の一覧順で前提が満たされた最初の未完了単位を選ぶ。再開候補と完了状態は全体計画を参照し、この指示ファイルに固定した候補を重複して記録しない。

F01 の部分積分では [構造文書](ARCHITECTURE.md#依存関係と実装の分担)にある SpinGlass の流用元と共有ガウス基盤の既存宣言を照合する。証明や定義を重複させず、原稿の `η ≤ α` の範囲を超える偏導関数の成長仮定を暗黙に追加しない。流用元の証明が存在することと、移植した Lean コードが検査済みであることは区別する。

複数担当で作業するときは同じ開始時点の独立した作業領域を使い、共有作業ツリー上の同時編集を避ける。同じファイルへの変更は担当補題と入力 API を先に分け、一人の統合担当が直列に取り込む。全体の進捗・Blueprint の更新もその担当に集約する。Lean 実装担当は原稿を編集せず、不一致は根拠付きで報告する。Blueprint は統合・検証済みの宣言に合わせて更新し、既存の未形式化ノードは計画として区別して残す。Verso の機械的検査は休止したままとする。明示的に別の作業を依頼された場合は、その範囲と承認条件を先に確認する。

## Lean の依存関係

共有の `SYK.Probability.GaussianConcentration`・`SYK.Model` と、利用する場合の `SYK.SuperConcentration` から `SYK.CLT` への依存を保つ。現行 `Main.lean` は `SYK.Annealed_FE.main_result` の入力構造も使う。CLT 側で共有部分を再定義せず、共有部分が CLT を `import` する循環も作らない。入力構造の変更は R02・F06 の仕様確定後に行い、W06 では依存先の再設計を行わない。モジュール名とファイル名は `UpperCamelCase` とする。

この依存方向は「共有部分の結果を CLT が利用する」という意味であり、共有部分が CLT をインポートするという意味ではない。大文字のモジュールパスは移行後の名称を含むため、実際のパスは移行状況と照合する。

Lean のコメントとドキュメント文字列では、`Theorem 1.2` や `Lemma 3.3` のような原稿編集で変わる番号ではなく、TeX の `\label{...}` をバッククォートで囲んで参照する。対応するラベルがない結果は勝手に命名せず、TeX にラベルを追加するか、現在ラベルがないことを明記する。

- 重要な方針決定は、関係する上記文書の該当節に理由とともに反映する。

情報量が増えてこれらの文書では管理できなくなった場合に限り、役割を再分割する。
