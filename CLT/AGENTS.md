## 正式な参照元

- `refs/CLT_SYK.tex` は現在の論文の親ファイルであり、共通のプリアンブルを記録する。`refs/sections/` は本文を記録する。両者を合わせたものを定理文の正式な参照元とする。
- `ARCHITECTURE.md` は意図した証明依存関係と各結果の現在の状態を記録する。
- `../EDITING_PLAN.md` は横断的な作業単位、その前提と状態を記録する。開始時に指定 ID と対応する詳細計画を読む。
- `EDITING_PLAN.md` は既知の問題、数学的な細目、作業の完了条件と現行の検証状態を記録する。完了済み作業の詳しい経緯は [作業履歴](../WORK_HISTORY.md) の該当節を参照する。
- Lean ファイルは、Lean のカーネルが検査した正確な定理文についてのみ証明状態を記録する。

これらが一致しない場合、黙って一つを選んだり統合したりせず、不一致を報告する。

## 保護する数学的内容

CLT の有限模型の証明は一般の `Params` と `MajoranaSystem`、漸近証明は `S : Setting q` を入力とする。`q` の偶数性と `4 ≤ q` は `S` のフィールドを用い、重複した入力を要求しない。Proposition 4.2 は `hFE : AnnealedInput q S` として仮定し、その構築を CLT の完了条件にしない。`Setting` に新しい仮定を追加しない。

`FiniteModel.lean` は抽象的な有限模型の定義・評価・モーメントを置く。`Normalization.lean` は標準表現との有限サイズの規格化照合だけを置き、`Main.lean` とその証明依存から import しない。標準模型専用の `Setting`、`AnnealedInput`、CLT、公理を追加せず、標準表現の再構成を抽象証明に持ち込まない。

明示的な承認なしに、`M_N`、`sigma_N`、`H_N`、`Z_N`、`Y_N` の定義、スケーリング `N^(q/2-1)`、極限分散、逆温度の範囲、相対ゆらぎ・標準化したゆらぎ・対数のゆらぎに対する中心極限定理（CLT）の区別、および各結果の収束の種類を変更しない。

各ゆらぎの定義、極限分散、中心化の差は `ARCHITECTURE.md` の「現行原稿の主張」と「対数 CLT の新しい経路」を参照する。

現行 CLT の主定理の実装・原稿は実数 `β` と高温条件 `|β| < βq` および `β ≠ 0` を用いる。以前の非負逆温度への移行案を理由にこの範囲を変更しない。共有模型の物理的 Gibbs・集中 API の `β : ℝ≥0` は維持し、CLT の実数逆温度の結果は必要な適用を明示して導く。解析の `z : ℂ` と確率論の `β : ℝ` は区別する。

CLT の規格化分配関数は一般の非空有限次元 `MajoranaSystem` の実際の次元で割る。標準表現への特殊化による原稿との対応と、一般表現への外部極限定理の適用可能性を別に照合する。有限模型の結果に、未証明の最終 CLT や `AnnealedInput` を使わない。

複素対数微分に現れる `Z z ≠ 0` は定理の仮定として明示し、零点のない領域が証明されていない段階で自動的に満たされるものとして扱わない。

## 証明と未完了事項の確認

証明を変更・説明する際は `ARCHITECTURE.md` の分解と依存関係を確認する。高次カオスの剰余項には、`refs/sections/higher-chaoses.tex` のラデマッハ変数による符号化と指数モーメントによる直接評価を用いる。対数 CLT は有効な本文の `Z_N≥1` と小確率事象による新証明を基準にする。`main-results.tex` の `\iffalse` 内の集中評価を使う旧証明は履歴であり、必須依存として扱わない。

作業前に `EDITING_PLAN.md` の未完了事項を確認する。定理文に関わる問題の調査と修正案の作成は、指定された範囲で進めてよい。ただし、その修正を単なる誤植修正として処理せず、定理文や採用する前提を変更する前に人間の研究者の承認を得る。判断事項は該当項目にまとめ、別の承認済み作業まで一律に停止させる前提にしない。

## 共同実装の着手条件

R01–R05 は原稿・外部入力の監査、F01–F08 は成果の枠であり、番号だけでは直ちに実装可能な証明仕様にならない。共同研究者から `F01 を進めて` などの短い依頼を受けた場合も、[全体計画](../EDITING_PLAN.md#共同実装の割当方法)と [担当別作業票](EDITING_PLAN.md#担当別作業票とコード整理)の該当節を読み、対応する監査、前提の統合、正確な定理文・入力、編集担当、検証対象を確認してから実装する。足りなければ指定課題内の調査と障害の報告まで進め、未承認の仮定・定理文を仮置きしてコードを書かない。単なる `CLT の続きを実装` という依頼では、全体計画の F01–F08 のうち前提を満たす最初の未完了な担当票を選ぶ。その票に必要な監査が未了なら、指定範囲の読み取り調査と不足事項の報告まで進める。R01 の原稿整理と原稿本文の編集は、明示的に担当を依頼された場合に限る。再開候補と完了状態は全体計画を参照し、この指示ファイルに固定した候補を重複して記録しない。

部分積分は共有ガウス基盤の既存宣言を利用し、原稿の `η ≤ α` の範囲を超える偏導関数の成長仮定を暗黙に追加しない。外部コードを流用するときは、流用元の証明と移植後の Lean 検証を区別する。

複数担当で作業するときは同じ開始時点の独立した作業領域を使い、共有作業ツリー上の同時編集を避ける。同じファイルへの変更は担当補題と入力 API を先に分け、一人の統合担当が直列に取り込む。全体の進捗・Blueprint の更新もその担当に集約する。Lean 実装担当は原稿を編集せず、不一致は根拠付きで報告する。Blueprint は統合・検証済みの宣言に合わせて更新し、既存の未形式化ノードは計画として区別して残す。Verso の機械的検査は休止したままとする。明示的に別の作業を依頼された場合は、その範囲と承認条件を先に確認する。

## Lean の依存関係

`SYK.CLT` は共有の `SYK.Probability.GaussianConcentration`・`SYK.Model` と、必要な場合の `SYK.SuperConcentration` を利用し、共有部分から CLT への `import` は作らない。現行 `Main.lean` は `SYK.Annealed_FE.main_result` を import せず、`prop:annealed-free-energy` に合わせた `AnnealedInput q S` を宣言する。

`Lemmas/` の探索は [README の案内](README.md#finding-a-lemma) から始める。宣言名と caller を `rg` で探し、対象の定理文と周辺の必要な証明だけを読む。型の確認には `#check` や `#print` を使い、巨大な `GaussianIBP.lean` や `Main.lean` を通常の補題利用のために全文走査しない。

補題 file は一つの数学的役割または proof layer に対応させ、再編では依存が閉じた一つの block ずつ移す。`Tool`・`Utils`・`Misc` のような新しい倉庫 file、宣言一覧だけの Lean file、既存定理の wrapper API は作らない。aggregate module が必要なら import-only とする。純粋な file 再編では公開宣言の名前・namespace・型・仮定・属性・規格化を保ち、古い path の互換用 module を作らず caller を更新する。`Preliminaries.lean` の `Main` import は、必要な定義を上流に抽出し caller を更新する場合にだけ解消する。

新 module と直接 consumer を個別に検査してから `lake build CLT` を実行する。

Lean のコメントとドキュメント文字列では、`Theorem 1.2` や `Lemma 3.3` のような原稿編集で変わる番号ではなく、TeX の `\label{...}` をバッククォートで囲んで参照する。対応するラベルがない結果は勝手に命名せず、TeX にラベルを追加するか、現在ラベルがないことを明記する。

## 文書の集約方針

最小構成を維持するため、独立した `proof_status.md`、`issue_register.md`、`decision_log.md`、`work_log.md` は現時点では作成しない。

- 横断的な実行単位の状態は `../EDITING_PLAN.md` だけで管理する。CLT 内に別の実行一覧は作らない。
- 原稿の証明構造と証明状態の概観は `ARCHITECTURE.md`、残作業と現行の検証状態は `EDITING_PLAN.md`、完了済み作業の詳しい検証根拠は `../WORK_HISTORY.md` の該当節を参照する。
- 問題、単位内の細目、未完了項目は `EDITING_PLAN.md` に記録する。単位間の優先順位は `../EDITING_PLAN.md` に集約する。
- 重要な方針決定は、関係する上記文書の該当節に理由とともに反映する。

情報量が増えてこれらの文書では管理できなくなった場合に限り、役割を再分割する。
