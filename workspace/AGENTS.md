# AGENTS.md

## 適用範囲と共有環境

このディレクトリは、複数の数学研究プロジェクトが Lean 4 の環境を共有するワークスペースである。このファイルには分野共通の規則を置き、このワークスペース内で対象までの経路にある下位の `AGENTS.md` を追加して適用する。

- ワークスペースの `lakefile.toml`・`lake-manifest.json`・`lean-toolchain` を使う。承認済みのローカル依存パッケージは自身の Lake 設定と `lean-toolchain` を持ち、依存版とツールチェーンを親と揃える。
- `.lake/` は配布・バージョン管理に含めないローカルキャッシュである。明示的な指示なしに、別の Lake プロジェクト、独立した依存キャッシュ、mathlib のコピー、`lean-toolchain` をサブプロジェクトに作らない。
- 新しい数学プロジェクトはローカル依存パッケージ、Lean ライブラリまたは名前空間として追加する。依存の追加・更新や上記設定3ファイルの変更前に、理由とワークスペース全体への影響を説明して承認を得る。不要なキャッシュ全体の再取得・全再ビルドは避ける。

## 数学と証明

- 明示的な指示なしに、定理の仮定・量化順序・型・結論を変更しない。偽、曖昧、形式化に不適切な主張を見つけたら報告し、黙って弱めない。
- 非形式的議論、計算、外部文献の入力、Lean のカーネルが検査した証明を区別する。正確な定理文の証明を未完成箇所なしで Lean が受理するまで、形式的に証明済みと述べない。
- `sorry`・`admit`・`axiom` や同等の未検証の仮定を導入しない。目標定理、その同値な言い換え、循環する依存を証明に使わない。
- 明示的な証明項と基本タクティクを優先する。`simp`・`ring`・`norm_num`・`linarith` 等は数学的役割が明確な局所目標に限り、`aesop`・`grind` 等の広範な探索は明示的な依頼なしに使わない。主要補題とその役割を説明する。
- 自明でない証明では、正確な主張・曖昧さ・反例の可能性・既存補題を確認し、編集前に短い計画を示す。一つの補題または限定した変更ごとに Lean で検査し、方針が失敗したらエラーと数学的障害を説明してから方針を変える。

## コードと編集

- 課題に必要な最小限の変更を行い、無関係な人間の変更を保持する。明示的な依頼なしに Git の commit・reset・rebase・既存変更の破棄を行わない。新しいファイルやディレクトリは依頼または管理上の必要がある場合に限る。
- 数学を直接読める具体的な定義・定理を既定とし、研究に必要な範囲を超えて一般化しない。抽象化は実際の複数利用、循環依存の回避、模型に依存しない結果の分離に必要な場合に限り、利用箇所または利点を説明する。
- 一つの用途だけの型クラス、既存定義を包むだけの構造・別名、定義や結果を結ぶだけの補題・モジュール階層を、将来の利用に備えて追加しない。`import` は必要最小限とし、共有すべき定義は必要な依存を持ち利用側へ逆依存しない共有層に一度だけ置く。ファイル分割そのものを目的にしない。
- 編集後に関係する差分を確認し、変更内容を要約する。

### 命名

新規宣言と再設計時の改名には次を適用し、無関係な既存宣言を一括改名しない。

| 対象 | 規則 |
| --- | --- |
| モジュール名の各部分・ファイル名、型・構造体・型クラス・`Prop` を返す述語 | `UpperCamelCase` |
| 通常の値・関数 | `lowerCamelCase` |
| 定理・補題・証明を格納するフィールド | mathlib に従う `snake_case` |

定理名に既存の宣言名を含める場合、その `lowerCamelCase` を分割せず一つの構成要素として保つ。

## 原稿との対応と検証

LaTeX は意図した数学と論証、Lean は記述された定義・定理文を記録する。仮定・規格化・量化・型・結論を照合するまで、Lean が論文の定理を検証したと述べない。未形式化の外部結果と条件付き定理はその状態を明記する。`h : P` から `Q` を証明しても `P` の証明にはならず、定理文の仮定と公理依存は別々に確認する。

Lean ファイルを変更したら、ワークスペースのルートから個別に検査する。

```bash
lake lean path/to/ModifiedFile.lean
```

`lake lean` は依存を先にビルドし、そのファイルのライブラリの `leanOptions` を適用する。`lake env lean` は環境を設定するだけなので、個別検査には使わない。

ライブラリへ影響する変更では関連する最小のビルド対象を使い、ワークスペース全体の変更では、各プロジェクトの規則が定める全体のビルド対象を完了前に実行する。重要な最終定理は `#print axioms` も確認する。残るエラー・関連警告・未完成証明・未解決目標・未検証の仮定を報告する。ビルド成功だけでは意図した数学との一致を保証しない。文書だけの変更では内容・参照・差分を確認し、Lean の再検査は必要な場合に行う。

## 文書と言語

用途に応じて必要な文書だけを置く。規則と短い解釈は `AGENTS.md`、現行仕様・設計理由・依存は `ARCHITECTURE.md`、未完了課題と完了条件は `EDITING_PLAN.md`、履歴は履歴文書、導出は原稿・ノートに置き、説明を重複させない。現行仕様・移行目標・証明済み結果を区別する。

三層以上、分岐・合流、複数の利用先がある依存関係は原則 Mermaid の `flowchart` で表す。正確な定理文・型・定数・数式は表や本文に記し、単純な一方向の関係には図を加えない。

- 会話はユーザーの問いの言語に合わせる。設定・計画・進捗・依存・問題管理の内部文書は日本語、公開用 README・Lean とそのコメント・LaTeX・研究成果物は英語で記す。
- 日本語で自然に表せる一般語は日本語にし、Lean・mathlib・Lake・Git・API 等の正式名称、識別子・コード・コマンド、原語が明確な専門語は保つ。
- 表現整理・翻訳では文意、指示の効力、数学の量化・仮定・記号・型・結論の強さを保つ。数学的曖昧さは勝手に決定せず報告する。
