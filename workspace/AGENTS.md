# AGENTS.md

## 適用範囲

このディレクトリは、複数の数学研究プロジェクトが一つの Lean 4 環境を共有するための統一的な Lean ワークスペースである。

このファイルには数学分野に依存しない共通規則だけを置く。サブディレクトリで作業する際は、そのディレクトリまでの経路にあるすべての `AGENTS.md` を読み、上位の一般規則に下位の個別規則を追加して適用する。

## 共有 Lean ワークスペース

- ルートの `lakefile.toml`、`lake-manifest.json` および `lean-toolchain` を全サブプロジェクトで使用する。
- `.lake/` はバージョン管理や配布の対象ではなく、Lake がワークスペースのルートに生成するローカルキャッシュとして扱う。
- 明示的な指示がない限り、サブプロジェクト内に別の Lake プロジェクト、独立した依存パッケージのキャッシュ、mathlib のコピー、または `lean-toolchain` を作らない。
- 新しい数学プロジェクトは、原則としてルートの Lake ワークスペースに Lean ライブラリまたは名前空間として追加する。
- 依存パッケージの追加・更新、または `lakefile.toml`、`lake-manifest.json`、`lean-toolchain` の変更前に、理由とワークスペース全体への影響を説明し、承認を得る。
- 必要がない限り、依存キャッシュ全体の再取得や全再ビルドを行わない。

## 数学的正しさ

- 明示的な指示がない限り、定理文の仮定、量化順序、型、結論を変更しない。
- 定理が偽、曖昧、または形式化に不適切である可能性を見つけた場合、黙って弱めたり修正したりせず、問題点を報告する。
- 非形式的な議論、数値・数式処理による計算、外部文献からの入力、および Lean のカーネルが検査した証明を明確に区別する。
- 正確な定理文について未完成の箇所を残さない証明を Lean が受理するまでは、形式的に証明済みと述べない。

## Lean の証明

- `sorry`、`admit`、`axiom`、または同等の未検証な仮定を導入しない。
- 目標定理そのもの、その同値な言い換え、または循環する依存関係を証明に使用しない。
- `intro`、`exact`、`apply`、`refine`、`constructor`、`cases`、`induction`、`rw`、`have`、`calc` など、明示的な証明項と基本的なタクティクを優先する。
- `simp`、`ring`、`norm_num`、`linarith` などの自動化は、数学的役割が明確な局所的な部分目標に限って使用する。
- 明示的に依頼されない限り、`aesop` や `grind` などの広範な証明探索を使用しない。
- 使用する主要な補題と、その数学的役割を説明する。

## 編集規則

- 現在の課題に必要な最小限の変更だけを行う。
- 研究上必要な範囲を超えて定義や定理を一般化しない。人間が読める主張を優先する。
- 明示的な依頼または管理上の必要がない限り、新しいファイルやディレクトリを作らない。
- 明示的に依頼されない限り、Git の commit、reset、rebase、既存変更の破棄を行わない。
- ユーザーによる無関係な変更を保持する。
- 編集後には関係する差分を確認し、変更内容を要約する。

## 検証

単一の Lean ファイルを変更した場合は、ワークスペースのルートから次を実行する。

```bash
lake env lean path/to/ModifiedFile.lean
```

Lean ライブラリに影響する変更では、利用可能なら関連する最小のビルド対象を実行する。ワークスペース全体に関わる変更の完了前には次を実行する。

```bash
lake build
```

残っているエラー、関連する警告、証明の未完成箇所、未解決の証明目標、未検証の仮定をすべて報告する。重要な最終定理では `#print axioms` を用いて公理依存を確認し、その結果を報告する。

ビルドの成功は Lean がコードを受理したことを意味するが、形式化された定理文が意図した数学を正しく表現することまでは保証しない。

## 自明でない証明の作業手順

1. 証明する定理を正確に言い直す。
2. 曖昧な点と反例になり得る場合を確認する。
3. 既存の定義と補題を調査する。
4. 編集前に短い証明計画を提示する。
5. 一度に一つの補題、または範囲を限定した一つの変更を扱う。
6. 意味のある変更ごとに Lean を実行する。
7. 方針が失敗した場合、大きな変更に進む前に Lean のエラーと数学的障害を説明する。

## Lean の命名

新規作成時、または再設計に伴って改名する際は、次の命名規則を適用する。

- Lean のモジュール名を構成する各部分とファイル名は `UpperCamelCase` とする。
- 型、構造体、型クラス、および `Prop` を返す述語の名前は `UpperCamelCase` とする。
- 通常の値と関数の名前は `lowerCamelCase` とする。
- 定理、補題、および証明を格納するフィールドの名前は、mathlib の規則に従う `snake_case` とする。

既存の宣言名を定理名に含める場合は、その宣言名の `lowerCamelCase` を分割せず、名前の一つの構成要素として保持する。

この規則を理由に、現在の課題と無関係な既存のプロジェクトやモジュールを一括改名しない。

## Lean コードの設計

- 数学的内容を直接読める具体的な定義と定理を既定とする。
- 複数箇所で実際に再利用する場合、循環依存を避ける場合、または模型に依存しない結果を明確に分離する場合に限り抽象化する。
- 一つの用途でしか使わない型クラス、既存の定義を包むだけの構造、別名、定義や結果を結び付けるためだけの補題、モジュールの階層を、将来に備えて追加しない。
- `import` は宣言が実際に必要とする最小限のモジュールに限定する。
- 依存を減らすために同じ数学的定義を重複させず、共有すべき定義は、依存関係上適切な最も下位の層に一度だけ置く。
- 抽象化を導入するときは、それを実際に利用する箇所または依存関係上の利点を説明する。
- 「最も下位の層」は、その定義に必要な依存関係を持ち、利用側へ逆向きに依存せずに置ける共有部分を指す。単にファイルを細かく分割することを目的にしない。
- 将来の再利用可能性のための抽象化よりも、現在の数学的議論との対応と人間による可読性を優先する。

## LaTeX と Lean の関係

- LaTeX 原稿は意図した数学的主張と論証を記録する。
- Lean は実際に記述された定義と定理文だけを検証する。
- 仮定、規格化、量化、型、結論を明示的に照合するまでは、Lean の定理が論文の定理を検証したと述べない。
- 未形式化の解析的結果を名前を付けた外部からの前提として切り出す場合、その状態を明記する。
- 外部からの前提、または条件付きの定理を、内部で証明済みの事実として表現しない。

例えば、外部結果を仮定 `h : P` として受け取って結論 `Q` を証明した場合、Lean が検証するのはその仮定の下での結論であり、`P` 自体ではない。`#print axioms` の確認と、定理文に残る仮定の確認は別々に行う。

## プロジェクト文書

大きな証明課題では、必要に応じて対象ディレクトリに、公開用の案内を記す英語の `README.md`、Codex と研究者が依存関係を共有する日本語の `ARCHITECTURE.md`、未完了作業を管理する日本語の `EDITING_PLAN.md` を置く。

文書数は最小限に保つ。一つの文書で十分に管理できる進捗、問題、履歴のために、個別のファイルを機械的に増やさない。

`AGENTS.md` には守る条件と、その解釈を特定する短い定義・注意点を置く。設計理由や依存関係は `ARCHITECTURE.md`、未解決事項と完了条件は `EDITING_PLAN.md`、数学的な導出は原稿や講義ノートに置く。詳しい説明は重複させず、必要な作業と参照先を示す。現行仕様、移行後の目標、証明済みの結果は区別して記述する。

三層以上の階層、分岐・合流、または複数の利用先を含む依存関係は、原則として Mermaid の `flowchart` で記述する。正確な定理文、仮定、型、定数、数式は図に埋め込まず、Markdown の表、コードブロック、または本文に記録する。単純な一方向の関係に図を追加しない。

## 言語方針

- ユーザーとの会話は、問い掛けが日本語なら日本語、英語なら英語で行う。
- Codex の設定、作業計画、進捗、依存関係、問題管理のための文書は日本語で記述する。これには `AGENTS.md`、`ARCHITECTURE.md`、`EDITING_PLAN.md` および同種の内部文書を含む。
- GitHub 等で外部公開される `README.md`、Lean コード、Lean 内のコメントとドキュメント文字列、LaTeX 論文、および公開用研究成果物は英語で記述する。
- Markdown の言語は拡張子ではなく用途で決める。Codex との協働用文書は日本語、公開用文書は英語とする。
- Lean、mathlib、Lake、Git、API の正式な識別子・コマンド・用語は翻訳しない。
- 数学的主張を翻訳するときは、量化順序、仮定、記号、型、結論の強さを変更しない。
- 翻訳に数学的な曖昧さがある場合は、勝手に決定せず報告する。
